# User Story: Verify a new user's email

**As a** new visitor who just registered
**I want to** confirm my email address via a verification link
**So that** my account becomes fully active and the app knows my email is real

## Context and assumptions

- Builds directly on US-001 (register a new user). A successful registration currently sets
  `status = active` immediately; this story changes that to `pending_verification` until the
  link is confirmed.
- No email-sending library is in the approved stack (`AGENTS.md`). This story stops at
  generating and validating the verification token; actually delivering it by email is a
  separate, later concern. For now the raw token (and the link a real email would contain) is
  returned in the registration response body as a temporary, documented stand-in for real email
  delivery — `AGENTS.md`'s "never log secrets or PII" rule is unconditional, so the token is
  never written to a log line, only ever returned directly to the caller who is entitled to it
  (the person who just submitted that registration).
- Verification is a single-use, expiring token, delivered as a URL query parameter
  (`GET /api/users/verify?token=...`), not a code the user types in.
- A user who is `pending_verification` cannot sign in yet (out of scope for this story to build
  the sign-in endpoint itself, but the status must exist so a future login story can check it).

---

## Acceptance Criteria

### AC1 — Registration issues a pending account and a token

> **Given** no user exists with email `ada@example.com`
> **When** I register with a valid email and password
> **Then** a user account is created with status `pending_verification`
> **And** a single-use verification token is generated and associated with that account
> **And** the raw token (and the link containing it) is returned in the registration response
>   body — never logged
> **And** no session cookie is set (the account isn't usable yet)

### AC2 — Successful verification activates the account

> **Given** a user exists with status `pending_verification` and a valid, unexpired token
> **When** I call the verification endpoint with that token
> **Then** the account status becomes `active`
> **And** the response is `200 OK`
> **And** the token cannot be used again

### AC3 — Unknown token is rejected

> **Given** no verification token matches the value supplied
> **When** I call the verification endpoint with that value
> **Then** verification fails with the message *"Invalid or expired verification link"*
> **And** the response status is `404`

### AC4 — Expired token is rejected

> **Given** a verification token exists but its expiry has passed (24 hours after issuance)
> **When** I call the verification endpoint with that token
> **Then** verification fails with the message *"Invalid or expired verification link"*
> **And** the response status is `404`
> **And** the account remains `pending_verification`

### AC5 — Already-used token is rejected

> **Given** a verification token has already been consumed once
> **When** I call the verification endpoint with that same token again
> **Then** verification fails with the message *"Invalid or expired verification link"*
> **And** the response status is `404`

### AC6 — Already-active account

> **Given** a user's account is already `active`
> **When** I call the verification endpoint with any token value tied to that account
> **Then** the response is `404` with the same message as AC3 (the token was already consumed by
>   the original verification, so this is indistinguishable from AC5 — no separate "already
>   verified" message)

---

## Definition of Done

- [ ] All acceptance criteria above are covered by automated tests.
- [ ] Verification tokens are cryptographically random (not sequential/guessable) and single-use.
- [ ] The token expiry (24h) is enforced server-side, not just documented.
- [ ] The raw token value is never written to a log line at any level — per US-001's
      never-log-secrets precedent for passwords. It is only ever returned directly in the
      registration response body, a temporary stand-in for real email delivery; revisit when a
      real mailer is introduced.
- [ ] Validation and status transitions run server-side only.

## Out of scope

- Actually sending an email (SMTP/3rd-party provider integration) — the raw token/link is
  returned in the registration response instead, per the assumption above.
- Resending/re-issuing a verification link for a user who lost the original.
- Sign-in / login endpoint itself (only the `pending_verification` → `active` gate this story
  depends on).
- Account lockout or rate limiting on the verification endpoint (US-001's registration rate
  limiter is unaffected and unrelated).
