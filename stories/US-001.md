# User Story: Register a new user

**As a** new visitor
**I want to** create an account with my email and password
**So that** I can sign in and use the app

## Context and assumptions

- Authentication lives inside the app — no Cognito, no Keycloak, no external identity provider.
- Credentials are email + password, stored in the app's own database.
- Passwords are hashed with bcrypt (cost ≥ 12) or argon2id. Never stored or logged in plain text.
- A successful registration signs the user in and sets an HttpOnly session cookie.
- Email verification is out of scope for this story (see *Out of scope* at the bottom).

---

## Acceptance Criteria

### AC1 — Successful registration

> **Given** no user exists with email `ada@example.com`
> **And** I am on the registration page
> **When** I submit the form with email `ada@example.com`, password `Str0ngPass1!` and matching confirmation
> **Then** a user account is created with email `ada@example.com`
> **And** the account status is `active`
> **And** a session cookie is set
> **And** I am redirected to the dashboard

### AC2 — Password is never stored in plain text

> **Given** I am on the registration page
> **When** I register with email `ada@example.com` and password `Str0ngPass1!`
> **Then** the stored password is a bcrypt hash
> **And** the stored value is not equal to `Str0ngPass1!`
> **And** the password does not appear anywhere in the application logs

### AC3 — Email is normalised before storage

> **Given** I am on the registration page
> **When** I register with email `  Ada@Example.COM  `
> **Then** the stored email is `ada@example.com` (trimmed and lowercased)

### AC4 — Email already registered

> **Given** a user already exists with email `ada@example.com`
> **When** I register with the same email
> **Then** registration fails with the message *"That email is already registered"*
> **And** exactly one user exists with that email
> **And** no session cookie is set

### AC5 — Password confirmation mismatch

> **Given** I am on the registration page
> **When** I submit password `Str0ngPass1!` and confirmation `Str0ngPass2!`
> **Then** registration fails with the message *"Passwords do not match"*
> **And** no user account is created

### AC6 — Invalid input is rejected

> **Given** I am on the registration page
> **When** I register with the values below
> **Then** registration fails with the matching message
> **And** no user account is created

| Email | Password | Expected message |
|---|---|---|
| *(empty)* | `Str0ngPass1!` | Email is required |
| `not-an-email` | `Str0ngPass1!` | Enter a valid email address |
| `ada@example.com` | *(empty)* | Password is required |
| `ada@example.com` | `Sh0rt1!` | Password must be at least 8 characters |
| `ada@example.com` | `passwordonly` | Password must contain a letter and a number |

### AC7 — Form state after a failed attempt

> **Given** my registration attempt has just failed validation
> **When** the page re-renders
> **Then** the email field still contains what I typed
> **And** both password fields are empty

### AC8 — Registration attempts are rate limited

> **Given** 5 registration attempts have been made from my IP in the last minute
> **When** I submit the form again
> **Then** registration fails with the message *"Too many attempts, please try again later"*
> **And** the response status is `429`

---

## Definition of Done

- [ ] All acceptance criteria above are covered by automated tests.
- [ ] Password hashing is done with a vetted library, never a hand-rolled hash.
- [ ] The email column has a unique index — the database enforces uniqueness, not just the application code.
- [ ] The session cookie is `HttpOnly` and `SameSite=Lax`.
- [ ] Validation runs server-side. Client-side validation is a convenience, not the gate.

## Out of scope

- Email verification / confirmation link (next story — would change the initial account status to `pending_verification`).
- Social login, SSO, magic links.
- Password reset and account recovery.
- Multi-factor authentication.
